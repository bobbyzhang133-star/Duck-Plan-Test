# Account and device sync — November 15, 2026

The current local website and existing iPhone/iPad project now share saved task settings through the account backend. This release is prepared locally; the public Worker, production database and installed physical devices have not been updated by this work. Use [OWNER-ACTIVATION.md](OWNER-ACTIVATION.md) for the remaining activation steps.

## Shared behavior

- Tasks retain their title, class, type, notes, priority, deadline, scheduled work time/duration, completion, importance and urgency. Logged minutes and deadline-reminder choices now use versioned `task_details`; alarm and normal-notification times, linked/manual modes, switches, timezone, sound and snooze use `work_alerts`.
- Existing classes, templates, class resources, organization preferences, goals, habits/check-ins and notes continue through their account routes. Layout choices, operating-system permissions and explicit device pause choices remain local to each installation.
- Older servers retain unsupported settings in an account-scoped device cache and show that they are not shared. When a compatible backend becomes available, the client adopts valid cached metadata without requiring another task edit.
- Adoption changes only canonical-null metadata with a matching `sync_revision`. Newer cloud settings win. It never uploads a stale full task, changes ownership, resurrects a deletion or changes completion. Cached alert history on completed tasks can sync, but completion keeps it ineligible for delivery.
- Valid existing native alert requests can supply missing metadata for unfinished legacy tasks. Their explicit times are retained; absent channels are not enabled. Loading an unconfigured task, or a completed legacy provider record, does not create new alerts.
- Every signed-in app installation applies the shared enabled settings when it receives the account snapshot, subject to its existing OS authorization and explicit local pause. Background refresh is a separately activated native capability; it never requests OS permission from the background.

## Closed-app behavior and limits

The native source includes APNs background hints, a native authenticated snapshot fetch and local AlarmKit/normal-notification reconciliation without requiring a visible WKWebView. The default free Personal Team build remains foreground-only: `DUCKPLAN_BACKGROUND_SYNC_ENABLED=NO` and no push entitlement. Push opt-in configurations are prepared for a team with suitable provisioning and APNs credentials.

A previously scheduled local alarm can be managed by the OS while the app is closed. Receiving a *new change from another device* while closed additionally needs the activated push build/backend and an OS-granted background opportunity. The Worker coalesces changes, limits accepted hints per installation to one per 20 minutes, retries unacknowledged snapshots and applies bounded retry backoff. APNs acceptance is not proof of delivery. Apple may delay background updates and does not relaunch a user-force-quit app for them; immediate or force-quit synchronization is not guaranteed. See [Apple's background update guidance](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app) and [delegate lifecycle behavior](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/application(_:didreceiveremotenotification:fetchcompletionhandler:)).

A native acknowledgment means the account snapshot was consumed, not that every OS alert request was registered. It can acknowledge a snapshot while alert application reports `needsAttention`. There is no separate closed-app retry for a transient OS scheduling failure after that acknowledgment; retry occurs on foreground/manual refresh or a later planner change. This avoids endless background pushes for persistent permission denial. Verify actual OS requests and delivery separately.

## Release boundary

No public deployment, remote migration, secret change, signing-team replacement or installed-phone update is authorized by preparing these files. The account owner must review and activate the existing Worker/database, then verify dedicated accounts and real devices as described in the owner guide. User preview storage and the user's existing simulator were preserved; fixtures and QA simulators are separate.
