Cause: landing/duck-interactions.js:149–172 clones a live .daily-task-card or .all-task-row, then appends that clone directly to document.body.

The Due/Work layout rules in landing/calendar-date-clarity.css:227–307 are scoped to #daily-task-panel, #view-home, and #view-tasks. The detached clone no longer matches them, so its icon sizing, grid and typography fall back to other styles.

The fresh measurements are conclusive: the live icons are 14×14px, while the outgoing echo icons expand to roughly 128px on desktop and 248px on phone.

Smallest fix: Give the outgoing completion snapshot a dedicated, self-contained layout class that preserves the full live-card geometry, including 14px icons, date columns, text wrapping, checkbox placement and theme variables. Avoid fixing only the SVG width while leaving the card's layout broken.

P1 — Feedback can celebrate an optimistic save

duck-interactions.js:128–182 captures the checkbox change and, after a zero-delay callback, checks the task's in-memory completed state before playing particles and reactions.

But planner-store.js:835–855 updates state optimistically before awaiting persistence. A failed write can subsequently roll back.

The existing feedback can therefore signal success even though the write is still pending. This is a source-level timing risk, not a failure reproduced in the current Playwright run.

Smallest fix: Separate immediate visual acknowledgement from confirmed success. Checking the box may respond instantly; success particles, the final-task notice and Undo should be linked to the successful completion operation.

P1 — Completion differs by entry point

app.js:1670–1675 completes checkbox tasks through the store. calendar-task-preview.js:126–146 also calls the store, but does not fire a checkbox change. The current effect only watches checkbox changes.

This means the Calendar preview receives a toast and status change but not the same completion animation. In the Tasks priority matrix, the checkbox observer can run, but the card selector does not recognize .matrix-task-card, so there is no normal card-exit snapshot.

Smallest fix: Give both paths a shared, presentation-only completion-feedback coordinator. Do not synthesize fake checkbox events or tie animation to all store updates.

The current code's finite particle cleanup remains a positive finding: both fresh local runs produced 10 ordinary particles and removed the echo and particles afterward. That is worth preserving.

The sequence distinguishes an action being acknowledged from the action being saved successfully. That's important both psychologically and technically.

The checkmark gives immediate feedback. The card's restrained exit communicates that the item has moved out of the active list. Particles and a success message provide a clear reward, but only after success is established. Undo supports recovery from accidental clicks.

A specific recommendation about final-task celebrations

When a user completes their final outstanding task for today, use the existing small Sigma congratulations card, but give it an Undo action.

The interface should communicate accomplishment without implying the student has finished everything in the account. For example:

Today's plan is complete!
You've finished all 3 tasks for today.
Undo · Dismiss

That is more accurate and useful than a generic large celebration.

If a task is completed for another day, the regular completion toast is enough.

4. Implementation plan for Codex

Stage 1 — Repair the completion snapshot (P1)

Touch duck-interactions.js, calendar-date-clarity.css and duck-theme.css.

Build a self-contained snapshot style shared with the live card's essential layout rules. Preserve width, height, typography, grid geometry and 14px date icons. Keep the clone inert, decorative, pointer-transparent and short-lived.

Do not merely force svg { width:14px } globally; that risks breaking Sigma illustrations and unrelated icons.

Stage 2 — Establish one presentation-only feedback coordinator (P1)

Keep planner-store.js's optimistic mutation behavior and existing persistence calls.

Use the same coordinator from checkbox completion in app.js and explicit completion in calendar-task-preview.js.

Capture the source element and previous task state before toggling. Apply immediate checkbox feedback, await the existing store promise, and trigger genuine success effects only when the operation is confirmed and still current.

If the save is slow and the source geometry is stale, skip the floating card exit and use a location-independent confirmation. Do not animate a stale snapshot across an unrelated page.

Stage 3 — Provide source-appropriate feedback everywhere (P1/P2)

The Calendar task panel, Dashboard and Tasks list use the normal card exit.

Calendar previews use a compact completion check and confirmation near the preview, not a fabricated checkbox event.

The Tasks priority matrix receives an appropriate small row or checkbox effect without assuming it uses .daily-task-card.

Complete all overdue should use one batch-level summary, rather than launching multiple particle bursts. Account refreshes, remote changes and automatic Axis imports must never be interpreted as user completion gestures.

Stage 4 — Undo, focus, rapid-toggle and error protection (P2)

Add a guarded Undo action through the existing toast API, preferably visible for approximately five seconds.

Use a per-task operation token, and cancel pending effects when completion is reversed, a newer operation begins, the route/account context changes, or the task is removed.

On persistence failure, let the store roll back, announce the error, restore a sensible focus target and suppress success particles and congratulations.

Keep any keyboard-focused control accessible without automatically focusing the success toast.

Stage 5 — Refine the final-task and Sigma feedback (P2/P3)

Keep the approved Sigma artwork and small congratulatory note. Include Undo and Dismiss without introducing a new full-screen overlay.

Show the note only when a confirmed user completion changes today's unfinished count from one to zero. Do not replay it on reload, sync or previously completed tasks.

Preserve motion-off and reduced-motion behavior: checked state, task movement, success status and Undo must remain usable without animation.

6. Final recommendation

I would prioritize three changes together for the first Codex iteration:

Fix the detached card's CSS geometry.

Make completion effects persistence-aware and consistent across entry points.

Add a clear Undo action to the success acknowledgement.

Those changes address the biggest usability problem: completion should feel good immediately, but its success message must always be trustworthy and reversible.

The current animation concept is worth retaining. The improvement is mostly about visual integrity, timing, consistency and error recovery—not adding more particles or making the duck dramatically larger.
