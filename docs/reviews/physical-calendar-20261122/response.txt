Initial verdict

A working prototype under $150 looks feasible, but a custom Raspberry Pi device is not necessarily the most cost-effective first prototype.

The strongest finding from the current supplier research is that an Android tablet already provides the touchscreen, processor, battery, speaker and Wi-Fi in one package. A Raspberry Pi requires those components separately and adds assembly and operating-system work.

For example, Walmart currently lists a 2026 7-inch onn Core tablet at $87, with 4GB RAM and Android 16. That is a materially better memory allowance than the proposed 1GB Pi for running a modern calendar interface. The tablet still needs a power adapter, mounting solution and custom alarm software before it becomes the intended appliance.

2. Which screen size is actually useful?

Illustrative size references, not tested DuckPlan hardware or actual scale comparisons.

For a child-facing wall calendar, I would not simply show seven densely packed DuckPlan timetable columns on a 7-inch screen. Instead, the dedicated device interface should prioritize a large day/date, the next task, an obvious alarm status and a short list of today's assignments. The existing DuckPlan website layout should remain unchanged.

For across-the-room viewing, a larger panel and much larger typography will matter more than pixel resolution. A 7–8-inch device is principally a desk companion or close-up wall display, not a substitute for a large family calendar several feet away.

The Pi's 1GB RAM is also a significant uncertainty. Chromium, Linux desktop services, GPU/display memory and DuckPlan's interface all share that limited space. It might handle a single optimized kiosk tab, but it could also become sluggish or reload under memory pressure. This must be benchmarked rather than assumed. The 4GB tablets offer more headroom, though they too remain untested with DuckPlan.

3. A real alarm must be separate from the browser

This is the most important software requirement. A screen with a speaker and an open DuckPlan webpage is not yet an alarm appliance.

The proposed design should be:

DuckPlan account and taskdata
Authenticated device sync
Local alarm database
OS-level alarm scheduler
Speaker rings
Child action
Stop
Snooze
Device calendar screen
Task changed or completed
Cancel / reschedule old alarm

The critical design rule is that the alarm scheduler must not depend on the calendar UI remaining open.

Android path — recommended for the first prototype

This requires new Android software, not the existing web app alone.

An Android companion could render a dedicated DuckPlan display while storing a local cache of upcoming alarm instructions. It should schedule alarms through Android's AlarmManager, use the device speaker to play a looping sound, provide full-screen or prominent Stop and Snooze controls, and restore pending schedules after boot.

Android's official documentation specifies that exact-alarm permissions require deliberate handling and that scheduled alarms are normally canceled at shutdown, requiring boot-time rescheduling. Some eligible calendar/alarm applications can use USE_EXACT_ALARM, while other apps must handle exact-alarm access appropriately; eligibility and behavior must not be assumed. 
developer.android.com
+1

For children, the interface should make Stop immediately accessible without navigating menus. On the first tablet prototype, large on-screen Stop/Snooze controls are acceptable. A dedicated physical Stop button would require a separate compatible accessory/interface and additional cost.

Raspberry Pi path — best for a later custom appliance

A Linux alarm daemon started by systemd could own the local schedule and directly play audio through the USB speaker, independent of Chromium. A GPIO-connected, debounced physical Stop/Snooze button would send commands to that service.

The daemon would need persistent local storage, restart recovery, clock/timezone management, missed-alarm policy, and reconciliation when DuckPlan tasks change.

Both paths require:

An authenticated way to obtain task/alarm changes, with safe credential handling and a local cache.

Exact instructions for which reminders produce an audible alarm. A date-only deadline must not silently become a midnight alarm.

Reliable cancellation after rescheduling, completion, deletion, account switching or sign-out.

Defined behavior when Wi-Fi is unavailable, including showing when schedules were last synced.

Existing DuckPlan web notifications and the iPhone's Apple AlarmKit implementation do not establish that these new Android/Linux alarms already work. They are separate platform development tasks.

Power limitation: A tablet's built-in battery provides some protection against unplugging, but long-term continuous charging and battery heat require testing. The proposed Pi has no battery backup: an outage stops the device and its alarm. An RTC alone would preserve time information, not power the speaker.

Likewise, neither of the proposed Android tablets has a verified downloadable duck-shaped enclosure that can simply be printed without measurement and modification. Their supplied cases or stands are usable for prototyping, not substitutes for a designed wall enclosure.

What the eventual Sigma duck case must add

It should use the approved Sigma duck identity while keeping the engineering practical: a removable front bezel and back shell, correct display mounting features, ventilation, accessible buttons, a speaker grille, secure power-cable strain relief, cable clearances and a stable desk/wall mounting method.

For a device meant for children, prioritize rounded edges, protected wiring, restrained sound volume, secure wall mounting and adult-only access to the electronics. Use an external certified power adapter instead of exposing mains wiring inside the print. For a battery-powered tablet, don't tightly enclose or obstruct a battery that could become hot.

No printable fit, structural strength or child-safety certification has been verified.

5. Recommended first steps and measurable acceptance tests

I would proceed in this order:

Settle the form factor before purchasing. Compare an 8-inch child-facing desk concept with a more distant wall-use mockup. If wall visibility from across a room is essential, do not force the design onto a small screen solely to meet the current budget.

Confirm an actual checkout basket. Check the tablet, charger, stand or included case, tax and shipping together for the intended delivery address. Approve nothing above $150 before the printed case.

Prototype the alarm architecture separately. Establish OS-level ringing, local persistence, Stop/Snooze, and reboot behavior before investing in a custom enclosure.

Build a device-specific DuckPlan display. Reuse current task data and Sigma artwork, but keep the display simplified and child-friendly. The existing website, backend and iPhone app should not be altered during this research phase.

Design the print only after measuring the selected hardware, charging and speaker clearances, mounting points, heat, and any physical buttons.

Final recommendation

For the first sub-$150 experiment, I would choose the onn 8-inch Kids Tablet, because its protective kickstand case and integrated components make it practical for young children without custom electronics. The 7-inch Core tablet is the cheaper alternative when the primary use is a desk companion.

If the long-term product goal is a distinctive 3D-printed Sigma duck wall appliance with real physical buttons, the Raspberry Pi route remains attractive—but I would not authorize the current Pi 4/Waveshare basket until its delivered cost, actual stock, screen compatibility and 1GB performance are resolved.
