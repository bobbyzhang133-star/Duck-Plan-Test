## Alarm/audio choices and software work

The USB speaker is a sound output, not an autonomous alarm scheduler. The Pi should run a boot-started local service with cached upcoming task/alarm data, a local sound file, Stop and optional Snooze, controlled independently of the browser. It must restore schedules after restart and reconcile edits/completion/sign-out. Define timezone/DST, missed-alarm and offline behavior. Do not rely only on a website timer, push delivery, autoplay or an open tab to establish reliable ringing.

For a thinner eventual case, an alternative is [Adafruit MAX98357A I2S amplifier, $5.95](https://www.adafruit.com/product/3006) plus [3W/4Ω enclosed speaker, product 4445, $3.95](https://www.adafruit.com/product/4445), plus wires/header assembly. [Official Pi setup guide](https://learn.adafruit.com/adafruit-max98357-i2s-class-d-mono-amp/raspberry-pi-usage). This replaces the USB speaker; do not add both to the baseline bill. It needs wiring, driver setup and volume/power testing; a bare speaker cannot connect directly to GPIO as an audio output. Keep an accessible physical Stop button and bounded volume.

An RTC can preserve time through a power interruption, but does not power the screen/computer/speaker. A battery/UPS is a separate requirement and cost if alarms must ring during an outage. Initial prototype assumption for review is continuous wall power and Wi-Fi, with cached schedules for an internet outage after time has been set; neither runtime nor offline capability is implemented/tested.
