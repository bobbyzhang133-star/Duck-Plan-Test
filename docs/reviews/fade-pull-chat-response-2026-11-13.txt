2. What should remain unchanged

The current view-transitions.js is a good foundation.

It already provides:

Correct sidebar-order direction with direction().

One native View Transitions API controller for outgoing and incoming snapshots.

A single guarded route commit during snapshot capture.

Sequence and account-owner protection against stale navigation.

Cancellation on content interaction, popup opening, resize and interruption.

Immediate navigation for reduced motion, touch, unsupported browsers and unsafe contexts.

Cleanup of temporary page-transition state.

In app.js:855–889, applyView() continues to own the actual route, selected navigation, URL and scroll behavior. navigateView() delegates visual transitions to the controller.

Do not replace these mechanisms with manual DOM cloning or a new animation engine. The smallest safe change is primarily in the page-transition CSS, with a small amount of configuration and test work.

3. Recommended motion direction

The new effect should communicate navigation direction without making the user perceive the pages as stacked physical slabs.

Calendar → Tasks

Old content lifts and fades; new content rises slightly into place.

Tasks → Calendar

Old content settles down and fades; new content arrives slightly from above.

Conceptual direction illustrations, not measured Apple animations or browser captures.

The sidebar, navigation controls and outer workspace frame should remain entirely stationary.

Apple's published motion guidance emphasizes purposeful, brief animation, a stable frame of reference and the ability to interrupt motion rather than wait for it to finish. That supports a restrained transition, but does not establish any exact iPhone unlock timing or CSS transform values.
